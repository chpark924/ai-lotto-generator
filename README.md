# 금손로또 (비용 최소화 / 서버리스 빌드)

기획서(`AI 로또 번호 생성 앱 기획서.pdf`)를 기반으로 하되, 다음 요청 사항을 반영해 구조를 조정했습니다.

- 최소한의 비용으로 최대한 많은 연산을 사용자 기기에서 처리 (비용이 안 들면 더 좋음)
- AI(LLM) 사용을 최소화 (기본값은 완전히 꺼짐)
- 자체 백엔드/DB 없이 완전 서버리스로 동작
- UI 문구·통계·안내 카드는 전문성 있어 보이도록 다듬을 것 (애매하거나 어설퍼 보이는 표현 지양, 수치/용어 설명을 명확히)
- 사용자는 기대감을 갖고 이 앱을 쓴다는 점을 항상 고려할 것: 법적/윤리적으로 필요한 확률 고지("모든 조합 확률 동일" 등)는 화면당 한 번(확률 카드·하단 안내 등)이면 충분하고, 결과 카드마다 반복 노출해 기대감을 과도하게 꺾지 않는다. 반대로 "조건 부합도·번호 편중 회피" 같은 전문적으로 보이는 설명은 만족감을 주므로 유지·강화한다.

## 기획서 대비 변경된 점

| 항목 | 기획서 원안 | 이 빌드 |
|---|---|---|
| 번호 생성 | 서버 권장 (중복 회피 위해) | 100% 기기(클라이언트) 내부 계산 |
| 백엔드 | Node.js + Supabase 등 자체 서버 | 없음. 모든 사용자 데이터는 기기에만 저장 (AsyncStorage) |
| 과거 당첨번호 | 자체 DB에 적재 | 동행복권 공개 조회 API를 앱이 직접 호출 + 기기 캐시 |
| 다른 사용자 인기번호 | 서버 집계 | 서버가 없어 실제 집계 불가. 대신 "일반적인 선택 편향(생일번호 쏠림 등)"을 정적 규칙으로 근사 — UI에 그 사실을 명시 |
| AI 사용 | 조건 해석 + 결과 설명 + 통계 해설 | 결과 설명 한 곳에서만, 기본값 OFF. 켜도 로컬 템플릿이 항상 무료로 우선 제공되고, AI는 사용자 본인의 API 키(BYOK)로만 호출됨 |
| 난수 생성 | node:crypto (서버) | expo-crypto의 기기 내 CSPRNG (서버 없이 동일한 안전성 확보) |

이 조정들은 모두 "서버 비용 0원, AI 비용 기본 0원, 최대한 사용자 디바이스에서 계산"이라는 요청을 만족시키기 위한 것입니다.

## 기술 스택

- Expo (React Native) + TypeScript + Expo Router
- Zustand (화면 간 임시 상태 전달용)
- AsyncStorage (기기 내 영구 저장)
- expo-crypto (안전한 난수)
- 백엔드 없음 / 자체 DB 없음

## 폴더 구조

```
src/lib/lottery/       순수 함수 번호 생성 엔진 (난수, 검증, 점수, 유사도, 확률, 행운번호, 주사위, 운명의 신)
src/lib/storage/       AsyncStorage 기반 로컬 저장 (저장번호, 제외번호 세트, 선호번호/설정)
src/lib/draws/         동행복권 공개 API 조회 + 캐시 + 통계 + 등수 계산
src/lib/ai/            결과 설명 전용 AI 연동 (기본 OFF, BYOK)
src/lib/notifications/ 추첨일 로컬 알림 예약 (expo-notifications, 서버 푸시 아님)
src/components/        공용 UI 컴포넌트
src/state/             화면 간 생성 결과 전달용 인메모리 스토어
app/                   Expo Router 화면 (탭 4개 + 생성 플로우 5종 + 결과 + 설정 + 선호번호 관리)
tests/                 Jest 단위 테스트 (엔진 정확성 검증)
```

## 구현된 기능 (기획서 24장 1차 MVP + 2차 + 3차 대부분)

1차 MVP
- 완전 무작위 생성 / 제외하고 생성 (직접 선택, 최근 N주 당첨번호 자동 제외, 제외번호 세트 저장·재사용)
- AI 조합 탐색 (즉시 생성 / 1만 회 / 3만 회 / 5만 회) — 이름과 달리 실제로는 로컬 난수 + 규칙 기반 점수 엔진이 담당하며, LLM 호출이 전혀 없음
- 추천 적합도 점수 (조건 일치도, 인기번호 회피, 내 저장번호와의 차별성, 분산도, 편향 완화)
- 로또 연구소 (최근 당첨결과, 번호별 출현 빈도, 장기 미출현 번호, 조합 패턴 통계)
- 결과 화면 확률 카드 (탐색 횟수와 무관하게 "최종 고유 저장 게임 수" 기준으로만 확률 계산)

2차
- 나의 행운번호 (생년월일 파생번호 + 선호번호 + 무작위 혼합, 번호별 출처 표시, SHA-256 해시 기반 재현 가능한 번호)
- 45면체 주사위 (탭/자동 굴리기, 특정 번호만 다시 굴리기)
- 선호번호 · 제외번호 세트 관리 화면 (내 번호 탭 → "선호번호 · 제외번호 세트 관리")
- 구매 예정/구매 완료 상태 관리, 회차 지정
- 당첨 결과 자동 확인 (내 번호 탭 진입 시 회차가 지정된 미확인 티켓을 자동으로 조회해 알려줌 — 수동 버튼도 유지)
- 내 번호 분석 (로또 연구소 탭)

3차 (서버 없이 구현 가능한 범위로 조정)
- 운명의 신: 목표 당첨자 수(1/5/10/20명, 30명 이상 대혼돈, 신의 뜻에 맡기기)를 "조합 인기도 목표값"으로 변환해 후보 중 가장 가까운 조합을 선택. 연속번호 설정, 선호번호 반영 여부 지원
- 주간 개인 리포트: 최근 7일간 저장한 티켓을 기반으로 게임 수 / 자주 고른 번호 / 홀짝 성향 요약 (로또 연구소 탭 상단)
- 결과 공유: 결과 화면과 내 번호 화면에서 React Native 기본 Share API로 번호 텍스트 공유 (추가 비용 없음)
- 추첨일 로컬 알림: expo-notifications로 매주 토요일 저녁 알림을 기기에 직접 예약 (서버 푸시 아님, 설정 탭에서 켜기/끄기)
- AI 자연어 설명: 이미 1차부터 지원 (기본 OFF, BYOK)

서버가 필요해 의도적으로 근사치로 대체한 항목 (완전 서버리스 원칙 유지):
- "사용자 인기번호 / 사용자 제외번호 / 다른 사용자 조합과의 겹침 방지"는 실제로는 서버에 쌓인 전체 사용자 집계가 있어야 정확합니다. 이 빌드는 서버가 없으므로 `buildPopularityHeuristic()`(생일번호 쏠림, 보기 좋은 패턴 등 일반적으로 알려진 편향을 근사한 정적 규칙)으로 대체했고, 모든 관련 화면에 "실제 타 사용자 데이터가 아니라 근사치"라는 안내 문구를 표시합니다.
- 로그인/계정 동기화는 하지 않습니다 (기기 로컬 저장만). 필요해지면 Supabase 무료 티어 등 최소 서버를 얹어 이 근사치들을 실제 집계로 교체할 수 있도록 계층(스토리지/점수 엔진)을 분리해 두었습니다.
- 알림은 로컬 예약 알림만 지원합니다. Expo Go에서도 로컬 알림은 기본적으로 동작하지만, 실기기 배포 시에는 `expo prebuild`/EAS Build로 만든 개발 빌드에서 테스트하는 것을 권장합니다 (Expo SDK 53 기준 Expo Go의 원격 푸시 지원이 제한적이나, 이 기능은 원격 푸시가 아닌 로컬 알림이라 영향이 적습니다).

## AI 비용에 대하여

- 기본 상태: AI 호출 0건. 결과 설명은 `src/lib/ai/explain.ts`의 `explainGameLocally`가 규칙 기반으로 즉시 생성합니다 (완전 무료).
- 설정에서 "AI 설명 사용"을 켜고 본인의 Anthropic API 키를 입력한 경우에만 `explainGameWithAi`가 호출됩니다. 이 비용은 앱 개발자가 아니라 키를 등록한 사용자 본인이 부담합니다(BYOK).
- AI에는 원문 개인정보나 전체 번호 목록 원본이 아니라, 구조화된 특징(`GameFeatures`)만 전달됩니다.

## 테스트

```bash
npm test          # Jest 단위 테스트 (생성 엔진, 확률, 유사도, 검증, 행운번호)
npm run typecheck # TypeScript strict 모드 타입 검사
```

`src/lib/lottery`는 순수 함수로만 구성되어 있어 네이티브 빌드 없이도 테스트할 수 있습니다 (`tests/mocks/expo-crypto.ts`가 테스트 환경에서 `expo-crypto`를 `node:crypto` 기반으로 대체합니다).

> 실제 검증 완료: `npm install`(테스트에 필요한 typescript/jest/ts-jest 등) 후 `npm test`를 돌려 **7개 테스트 스위트, 44개 테스트 전부 통과**를 확인했습니다 (생성 엔진의 범위/중복 없음/제외·필수번호 반영, 확률·탐색 비율 공식, 패턴 검증 함수, 유사도 계산, 검증 규칙, 행운번호 파생 및 해시 재현성, 운명의 신 시나리오 적합도 계산). 이 과정에서 `src/lib/ai/explain.ts`(AI 응답 파싱 타입)와 `src/lib/storage/storage.ts`(암시적 any)의 실제 타입 버그 2건을 발견해 수정했고, ts-jest가 `expo-crypto`를 타입 레벨에서도 인식하도록 `tsconfig.jest.json`을 추가했습니다. 전체 앱(Expo/React Native 포함) 의존성 설치는 트리가 커서 이번 환경에서 끝까지 받지는 못했지만, 핵심 로직은 실행 기반으로 검증되었습니다. `smoke_test.mjs`는 의존성 설치 없이도 같은 핵심 공식을 재확인할 수 있는 보조 스크립트로 계속 포함되어 있습니다.

## 참고: 과거 당첨번호 API

`src/lib/draws/drawApi.ts`는 동행복권이 공개적으로 제공하는 비공식 조회 엔드포인트(`getLottoNumber`)를 기기에서 직접 호출합니다. 모바일 앱은 브라우저 CORS 제약이 없으므로 별도 프록시 서버가 필요 없습니다. 다만 비공식 엔드포인트이므로 정책
